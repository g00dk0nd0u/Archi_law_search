# CODEX_USAGE

このリポジトリを法令調査に使うときは、必ず `data/laws.db` を根拠にして確認します。
一般知識だけで法令回答せず、検索結果にない内容は「現在の本データベース上では確認できません」と明記してください。

## 基本ルール

- 法令調査では必ず `python -m cli.search_laws` を使います。
- macOS などで `python` が使えない場合は `python3 -m cli.search_laws` に読み替えます。
- Windows、macOS、Codexクラウド環境で Python コマンド名が異なる場合があります。
- 条番号が分かる場合は `--article` を使います。
- `--article` は前方一致検索であり、枝番条文も含めて返ります。
- 法令が分かる場合は `--law-id` を優先します。
- キーワード調査は `--query` を使います。
- 初回検索で不十分な場合のみ、検索語を変えて最大1回だけ再検索します。
- 回答には、法令名・条番号・条名・該当原文を含めます。
- 関連条文が複数ある場合や原文が長い場合は、チャットに原文全文を貼らず、原則として `output/` 配下の `.txt` に原文一覧を出力します。
- 原文と解釈を混ぜません。
- 一般知識だけで法令回答しません。二次的な情報の不確定なウェブ利用は原則不可です。

## 回答フォーマット

法令調査の回答は、検索結果をそのまま並べず、原則として次の Markdown 形式に整理します。

```md
## まとめ

（DBで確認できた内容だけを使い、制度の全体像・分類・意味が分かる短い解説を書く）

## 根拠条文

### 1. 法令名 条番号（条名）

（この条文が何を定めているかを1行で書く）

## 原文

原文一覧は次のtxtに出力しました。

`output/xxxxx.txt`
```

複数条文が関係する場合は、条文ごとに分けます。

```md
## まとめ

（複数条文を踏まえ、まず分類名や呼び方、その分類の目的、どの法・施行令に接続するかを自然文で短く書く）

## 根拠条文

### 1. 建築基準法 第五十二条（容積率）

（この条文が何を定めているかを1行で書く）

### 2. 建築基準法施行令 第二条（面積、高さ等の算定方法）

（この条文が何を定めているかを1行で書く）

## 原文

### 建築基準法 第五十二条（容積率）

（該当項単位で全文。短ければ条全体。）

### 建築基準法施行令 第二条（面積、高さ等の算定方法）

（該当項単位で全文。短ければ条全体。）
```

## 実行環境差

- CLI実行は通常 `python -m cli.search_laws` を使います。
- macOSなどで `python` が使えない場合は、`python3 -m cli.search_laws` に読み替えます。
- Windows、macOS、Codexクラウド環境で Python コマンド名が異なる場合があります。

## 使い方

### 条番号が分かる場合

```bash
python -m cli.search_laws --law-id 325AC0000000201 --article 第五十二条 --json-pretty
```

`--article` は前方一致なので、`第五十二条` を指定すると `第五十二条の二` などの枝番条文も一緒に確認できます。

### 法令名で絞る場合

`--law` は、DB内に完全一致する法令名があるときは完全一致で検索し、完全一致がないときだけ部分一致にフォールバックします。

```bash
python -m cli.search_laws --law "建築基準法" --article 第五十二条 --json-pretty
```

### キーワードで調べる場合

```bash
python -m cli.search_laws --query "容積率 前面道路" --limit 10 --json-pretty
```

### 原文全文を txt に出力する場合

複数条文や長い条文を扱うときは、最初から `--export-txt` を使います。原文全文は `output/` 配下の txt に保存し、チャットには `まとめ / 根拠条文 / 原文txt保存先` だけを書きます。

```bash
python -m cli.search_laws --query "階段" --limit 20 --export-txt output/law_refs_stairs.txt
```

`output/` がなければ自動作成されます。`--export-txt` にパスを省略した場合は `output/law_search_results.txt` が使われます。

txt には、検索条件、各条文の見出し、DB本文がそのまま UTF-8 で保存されます。要約ではなく原文一覧を出します。

`--export-txt` 使用時の標準出力には `article_text` を含めず、次のような軽量JSONだけを返します。

```json
{
  "count": 1,
  "export_txt": "output/law_refs_stairs.txt",
  "results": [
    {
      "law_title": "建築基準法施行令",
      "article_number": "第百十二条",
      "article_title": "（防火区画）"
    }
  ]
}
```

## 回答作成時の注意

- 先にまとめを書きます。
- DBで確認できた内容だけをまとめに書きます。
- `## まとめ` は検索結果一覧ではなく、ユーザーが制度の全体像を理解できる短い解説にします。
- `## まとめ` では、まず実務上・制度上の呼び方や分類を示し、その分類が何を目的にしているかを短く書きます。
- `## まとめ` では、どの法・施行令に接続しているかを自然文で示し、いきなり条文番号だけを箇条書きしません。
- 複数分類がある場合は、違いを明示的に聞かれていなくても、分類名と目的をまとめに書きます。
- 条文番号の列挙は `## 根拠条文` に回し、原文は `## 原文` に回します。
- `## まとめ` は短くしすぎず、原則として2〜6文程度で「何の話か」が先に分かるように書きます。
- 比較が必要な場合だけ、`## まとめ` の後に比較表を入れてよく、比較表は必須ではありません。
- 条名は `article_title` や条文冒頭から確認します。
- 原文は改変しません。
- 原文は省略しすぎません。最低でも該当する項単位で全文を出します。
- 短い条文であれば、条全体を全文で出します。
- txtは要点ではなく原文一覧にします。
- 号が論点の場合でも、必要に応じてその号だけでなく、対応する項全体を確認できる形で出します。
- `...` による省略は原則避けます。
- どうしても省略する場合は、省略箇所を明示し、意味が変わらない範囲に限定します。
- DBで確認できない内容は、「このデータベース上では確認できません」と書きます。
- 網羅できない場合は、「このデータベース上で確認できた範囲では」と書きます。
- 実務上の補足は原則として書きません。
- DB外の推測を書く場合は、必ず `DB外の補足` と明示します。
- 「代表的には」「主に」「など」「おそらく」「たぶん」はなるべく使いません。
- 原文と解釈を混ぜません。
- ユーザー向けの最終回答には、検索過程やコマンド実行回数を原則として書きません。
- MEMORY.md など内部参照はユーザー向け回答に出しません。
- 最後に不要な提案や「必要なら〜」は書きません。

## txt出力を優先する目安

- 関連条文が3件以上ある
- 原文が長い条文を含む
- 表形式の条文を含む
- 第112条、第121条、第123条など長大な条文を含む
- ユーザーが「一覧」「関連条文」「気をつけるポイント」と聞いている
- 質問が個別条文確認ではなく、テーマ調査である

## 回答前チェック

- DBを検索したか
- 条文番号を確認したか
- 条名を確認したか
- 原文を出したか
- 原文が最低でも該当項単位になっているか
- 省略がある場合、省略箇所を明示したか
- DB外の説明を混ぜていないか
- 回答が `まとめ / 根拠条文 / 原文` の形になっているか
